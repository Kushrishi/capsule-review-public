## Why the archive is technically manageable

The full 31.99 GB is split into **10 independent solid compression blocks**. Nine are ~3.44–3.54 GB, and the last is ~630 MB. Their compressed lengths, plus the source headers, reconcile *exactly* to the official archive size. Each block's uncompressed content is about 4.29 GB, except the final block. Compressed blocks can be examined one at a time with a byte-for-byte sparse-file reconstruction; block-level correctness still requires live transfer and 7z decoding/CRC verification.

The first block contains **all 7,478 recorded exam-21 source images**, plus part of exam 22. This makes exam 21 a self-contained, bounded first real-image acquisition of **3,474,498,092 compressed bytes**, rather than a 32-GB all-or-nothing download. Ordinary GitHub-hosted private runners have around 14 GB storage, so the code streams only that one block into a sparse logical archive and retains only selected verified images. Larger transfers are never silently enabled. Subsequent blocks require separate source receipts and artifact-retention planning.

## One-block real-image proof and limitations

The archived source-only workflow [`galar-block0-acquisition.yml`](../archive/research-workflows/galar-block0-acquisition.yml) was restricted to examination 21 and one verified block. It first validates the original source ZIP and reproduces the private selection digest, then revalidates the HTTP 206 index and frame-to-archive filenames *before* requesting the larger compressed block. After the bounded transfer, 7z extraction/CRC, PNG decoding, source-byte SHA-256 and package ZIP CRC must all pass. The resulting data remain in a private temporary GitHub Actions artifact and then must be archived outside the repository; the routine never commits medical images or per-image labels.

If the block proof succeeds, it does **not** verify the full-archive upstream MD5, because the other nine blocks have not been transferred. Complete source checksum verification requires streaming all compressed blocks and the headers in their original byte order. A failed partial block does not justify lowering integrity checks or accessing evaluation studies 11–20 or 61–80.
